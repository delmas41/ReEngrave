## 1. What was wrong, in one line

`merge_additions.check_row` proved a map by running `page_normalise.normalise`
on the row's own trimmed truth **before writing**; `server.py` checked only the
cheap structural facts — every part named once, no part twice, every staff
decided — and **never called `page_normalise` at all**. So a row could go green
staff by staff, be marked `done`, and refuse at merge time with the whole pass
already spent. That is not hypothetical: two `page_normalise` faults did
exactly that to Mahler p3 and p4.

## 2. The repair: ONE prover, two callers

`merge_additions.prove_normalises(row_id, staves, source_reference=...)` is now
the single place `page_normalise` is asked anything, and both consumers call it.
`server.py` **imports** it — it does not re-implement it, and a test asserts
that `page_normalise.normalise(` appears nowhere in the server, because a second
call site is a second implementation waiting to drift.

⚠️ **One deliberate asymmetry, and it is in the shared function's docstring.**
The prover distinguishes *refused* from *unavailable*:

| result | `merge_additions` | the UI |
|---|---|---|
| `page_normalise` REFUSED the map | blocks the write | **blocks `done`** |
| the proof could not RUN (no `<row>.truth.musicxml` on this machine) | blocks the write | **warns only** |

The merge step is about to write hand-verified truth and must not write what it
could not prove. The UI writes only the additions file, and blocking Sean's
keystroke over a fixture missing from this machine would cost more than it
protects — the merge step still refuses afterwards. Both halves are pinned by
tests so the asymmetry stays a decision rather than a drift.

## 3. ⚠️ It may never cost a verdict — three mechanisms

Sean's decisions are irreplaceable and the proof is a nicety beside them.

1. **Nothing runs on the save path.** A `PATCH` stores the verdict and returns;
   the proof is computed afterwards on a worker thread. A source-level test
   asserts `store.save()` precedes the validation call in *every* mutating
   route, because a behavioural test would only exercise the route its fixture
   happened to take.
2. **A prover that raises is caught** and reported as `unavailable` — *"the
   normalisation check could not run"* — never propagated into a request, and
   `done_problems` returns `[]` for it. Pinned by a test that makes the prover
   throw.
3. **`done` is refused, not the save.** Sean can always keep working, switch
   rows, and come back.

## 4. Is it interactive? Measured, on the real app

The proof itself is **0.18–0.57 s** (Mahler's 38-part truth 0.35–0.57 s, Bach
0.18 s). Round trips through the actual FastAPI app, 12 samples each:

| request | median | max |
|---|--:|--:|
| `/api/index` (proof deliberately skipped — 5 rows would pay it 5×) | 1.1 ms | 1.8 ms |
| `GET` a row, proof cached | 1.7 ms | 2.6 ms |
| **`PATCH` a verdict — the keystroke of the whole pass** | **3.3 ms** | 4.2 ms |
| `PATCH` that CHANGES the map (starts a worker) | 2.8 ms | 203.9 ms |
| `GET` while a proof is mid-flight | 3.6 ms | 221.8 ms |

⚠️ **The confirmation keystroke never re-runs the proof, and that is the whole
performance story.** The cache is keyed on a fingerprint of the MAP — each
entry's `name` and `parts` — and **not** on the verdicts, so `t`/`f` on twenty
staves is twenty cache hits and one proof for the row. A test pins that
`fingerprint` ignores `verdict` and notices a changed `parts`.

The ~0.2 s maxima are GIL contention with the worker and occur only in the
~0.5 s window after an actual map edit. `done` on a cached proof answered in
**2 ms**; `done` is also the one place that waits, because it is one deliberate
keystroke.

## 5. ⚠️ §A00 — does the gate reject anything it should not? No.

Before believing any refusal, the check itself was asked of the population known
to be good:

* **all 15 rows already merged into `works.json`: accepted, 15 of 15.**
  Beethoven 18→12/11, Dvořák 15→15, Brahms 21→14.
* **all 5 proposals the UI ships, unedited: accepted, 5 of 5.** Mahler 38→21,
  38→15, 38→21, 38→21; Bach 11→11.

So the gate is silent through a pass that confirms the proposals, and fires only
where Sean's own edit would actually break the map. Zero false refusals.

## 8. A second consumer, and what that changes

`page_normalise` had **zero production consumers**, one benchmark-side gate on
human work, and nothing else. It now has two callers of the same gate. The
module is still not in the pipeline — but "test-only" was always the wrong
label for something that decides whether a human's afternoon can be recorded,
and there are now two places where that is true and one implementation behind
both.
