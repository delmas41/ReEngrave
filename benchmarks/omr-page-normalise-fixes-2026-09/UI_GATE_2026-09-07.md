## 1. What was wrong, in one line

`merge_additions.check_row` proved a map by running `page_normalise.normalise`
on the row's own trimmed truth **before writing**; `server.py` checked only the
cheap structural facts — every part named once, no part twice, every staff
decided — and **never called `page_normalise` at all**. So a row could go green
staff by staff, be marked `done`, and refuse at merge time with the whole pass
already spent. That is not hypothetical: two `page_normalise` faults did
exactly that to Mahler p3 and p4.

## 2. The repair: ONE prover, two callers

`merge_additions.prove_normalises(row_id, staves, source_reference=...)` is now
the single place `page_normalise` is asked anything, and both consumers call it.
`server.py` **imports** it — it does not re-implement it, and a test asserts
that `page_normalise.normalise(` appears nowhere in the server, because a second
call site is a second implementation waiting to drift.

⚠️ **One deliberate asymmetry, and it is in the shared function's docstring.**
The prover distinguishes *refused* from *unavailable*:

| result | `merge_additions` | the UI |
|---|---|---|
| `page_normalise` REFUSED the map | blocks the write | **blocks `done`** |
| the proof could not RUN (no `<row>.truth.musicxml` on this machine) | blocks the write | **warns only** |

The merge step is about to write hand-verified truth and must not write what it
could not prove. The UI writes only the additions file, and blocking Sean's
keystroke over a fixture missing from this machine would cost more than it
protects — the merge step still refuses afterwards. Both halves are pinned by
tests so the asymmetry stays a decision rather than a drift.

## 3. ⚠️ It may never cost a verdict — three mechanisms

Sean's decisions are irreplaceable and the proof is a nicety beside them.

1. **Nothing runs on the save path.** A `PATCH` stores the verdict and returns;
   the proof is computed afterwards on a worker thread. A source-level test
   asserts `store.save()` precedes the validation call in *every* mutating
   route, because a behavioural test would only exercise the route its fixture
   happened to take.
2. **A prover that raises is caught** and reported as `unavailable` — *"the
   normalisation check could not run"* — never propagated into a request, and
   `done_problems` returns `[]` for it. Pinned by a test that makes the prover
   throw.
3. **`done` is refused, not the save.** Sean can always keep working, switch
   rows, and come back.

## 4. Is it interactive? Measured, on the real app

The proof itself is **0.18–0.57 s** (Mahler's 38-part truth 0.35–0.57 s, Bach
0.18 s). Round trips through the actual FastAPI app, 12 samples each:

| request | median | max |
|---|--:|--:|
| `/api/index` (proof deliberately skipped — 5 rows would pay it 5×) | 1.1 ms | 1.8 ms |
| `GET` a row, proof cached | 1.7 ms | 2.6 ms |
| **`PATCH` a verdict — the keystroke of the whole pass** | **3.3 ms** | 4.2 ms |
| `PATCH` that CHANGES the map (starts a worker) | 2.8 ms | 203.9 ms |
| `GET` while a proof is mid-flight | 3.6 ms | 221.8 ms |

⚠️ **The confirmation keystroke never re-runs the proof, and that is the whole
performance story.** The cache is keyed on a fingerprint of the MAP — each
entry's `name` and `parts` — and **not** on the verdicts, so `t`/`f` on twenty
staves is twenty cache hits and one proof for the row. A test pins that
`fingerprint` ignores `verdict` and notices a changed `parts`.

The ~0.2 s maxima are GIL contention with the worker and occur only in the
~0.5 s window after an actual map edit. `done` on a cached proof answered in
**2 ms**; `done` is also the one place that waits, because it is one deliberate
keystroke.

# The strip marker was pointing at the wrong staff (2026-09-07)

Sean, at the tool: *"the layout looks correct, just the highlight is off
positionally."*

## ⚠️ The arithmetic lead was FALSIFIED before anything was changed

The suspicion was that `placeHighlight` re-derives the crop origin and
disagrees with `build_cache` — `int()` before vs after, `Math.trunc` vs
`int`, the `-3` fudge. Measured over every system of all five rows:
**`py_yoff - js_yoff == 0` everywhere**, and the worst band-to-marker delta is
**3.0 px, which IS the deliberate `-3`**. The two implementations agreed. That
was not the bug.

## What it actually was: an ORDINAL join

`placeHighlight(img, hl, sys, CUR)` did `sys.staves[CUR]` — it indexed the
**detected bands** by the **map entry's** number. Those are different index
spaces the moment a page's map is longer than its band list. Read live out of
the running page:

| | |
|---|---|
| row | `mahler-sym5-mvt1-local-p2` (the row the UI opens on) |
| map entries | **21** |
| detected bands | **19** |
| selected entry 14 | `Kleine Trommel` |
| band it marked | `instrument: "Violin"`, y0 **4416** |

`instancesFor` already joins entry → printed staff **by parts** through the
hand-read lineup, and abstains where the lineup and detection disagree about a
system — a rule works.json put there after a Trumpet entry silently claimed the
Es-horn staff on Brahms p2. The overlay was the one thing not obeying it.

## The fix, and why repair rather than remove

Both were offered. **Repaired**, because the Python boxes number the *detected
bands* (0…18) while Sean is deciding *map entries* (0…20) — on exactly the rows
where those disagree, the strip alone cannot say which slot he is on, so
deleting the overlay makes the worst rows worse. What it must not do is point at
the wrong staff, and now it does not:

* the band is found through `instancesFor`, by parts;
* it **hides** when the join abstains — and the caption says why:
  `system 1 — slot 14 is not marked here: Kleine Trommel (lineup and detection
  disagree about this system: 21 read vs 19 detected)`;
* every system is marked, not only the proposal's, since the join abstains per
  system on its own.

And the structural half, which was a real (if currently harmless) desync:
`build_cache.strip_crop_geometry` is now **the one place** the crop is
computed. `write_images` cuts with it, the server stamps it onto each seed
(`sys.crop`), and the browser **reads** `y_off`/`divisor` instead of
recomputing them. Stamped at request time, so **no cache rebuild is needed**.

# The merge: `parts` is ORDERED, and sorting it renames three staves Piccolo

Sean finished the pass — p3 (15), p4 (21), p5 (21) and Bach (11) `done`, 82
slots confirmed; p2 left at 14/21, correctly, since works.json already carries
it verbatim. `merge_additions` then refused three of the four for `parts` "not
sorted-unique", and the proposed repair was to **sort on write**.

## ⚠️ Measured before sorting anything, and it is NOT a no-op

`page_normalise.py:369` — `keep = parts[idx[0]]`, and the rest are merged into
it. So the first index chooses which reference part the merged staff **is**.
Priced on Sean's own confirmed maps (`probe_parts_order.py`):

| row | as confirmed | sorted | delta |
|---|--:|--:|--:|
| mahler p3 | 2159 | 2156 | **−3** |
| mahler p4 | 3209 | 3228 | **+19** |
| mahler p5 | 2300 | 2292 | **−8** |
| bach | 6148 | 6148 | +0 |
| **total** | **13816** | **13824** | **+8** |

And the musical diff says exactly what moves (`probe_parts_order_diff.py`,
compared on parsed content — **never bytes**, since music21 mints a random
`<score-instrument id>` per write and already fooled one comparison today):

| row | entry 0 | as confirmed | sorted | bars differing |
|---|---|---|---|--:|
| p3 | `Fag. 1/2` | `Zwei Fagotte.` | **`Piccolo`** | **0** |
| p4 | `Hoboen 1.2.3` | `Drei Hoboen.` | **`Piccolo`** | **0** |
| p5 | `A-Klar. 1.2` | `Drei Klarinetten in A` | **`Piccolo`** | **0** |

**Not one note moves — 15/15, 21/21 and 21/21 parts are bar-for-bar
identical.** What sorting does is put the silent, tacet-folded Piccolo first,
so three printed staves come back named after a part that does not sound on the
page; musicdiff then re-pairs on the wrong name, which is the ±edits. A sorted
map is not a tidier spelling of the same truth.

## So the gate was right to fire and wrong about why

`sorted(set(p)) != list(p)` conflated **uniqueness** — a real invariant, a
staff cannot carry one part twice — with **sortedness**, a canonicalisation
that moves the answer. Split: uniqueness still refuses, sortedness no longer
does. The UI's editor stopped sorting too (`list(dict.fromkeys(...))`), so a
future hand edit cannot introduce the same rename. Both pinned, along with
proof that a genuine problem still refuses — a repeated part, a part named by
two staves, an unaccounted part, an empty map, a nameless entry.

⚠️ **The principled follow-up, deliberately NOT done here:** `keep` is chosen
by list POSITION, which is the only reason an ordering can carry meaning. An
explicit rule — prefer the first part that SOUNDS on this page — would agree
with the human's order on all three rows and make ordering irrelevant. It
changes the transform, so it needs the Dvořák +0 and engraved no-op controls
before it ships, and it is not what unblocks a finished pass.
