## Fix 1 — a part's opening clef is not always measure 0's

Ranked item 2. `tools/omr/export.py`.

### The mechanism, which is one step narrower than RESULTS.md states it

RESULTS.md says the export takes each part's clef from measure 0 and therefore
"all fifteen parts export as G2". Read against the file, the MusicXML is
slightly better behaved than that and it does not change the diagnosis: seven
parts open G2 **and then emit a clef change at measure 2** to the clef they
should have opened in (`m1:G2,m2:F4`). The other eight are treble throughout and
correct. LilyPond has no such recovery — `_lily_staff_block` emits one `\clef`
for the whole staff from `staff["clef"]` — so on that exporter all fifteen
Dvořák staves really are treble.

Underneath, `staff["clef"]` is `'treble'` on all fifteen staves, and so is
`measures[0]["clef"]`, while `measures[1..8]["clef"]` carries the right answer
on seven of them. The reason is visible in the detections:

| | measure 0 | measure 1 |
|---|---|---|
| Dvořák staff 3 (Fagotti) | `['structural']` — a brace at conf 0.33 | `['accidental','clef','notehead','rest','structural']` |
| Dvořák staff 1 (Flauto II) | `[]` — nothing at all | `['accidental','clef','rest','structural','time_sig_digit']` |

Every one of the fifteen leading cells holds **no clef detection**: eleven hold
only `structural`, four hold nothing. `transcribe` reads a clef where one is
printed, and system furniture prints none — so measure 0's clef field is the
positional default, and measure 1's is a reading.

### The rule

`export._first_clef_bearing_measure(measures)` returns the index of the first
measure that could have READ a clef or could have USED one:

- it holds a `clef` detection — its clef is a reading, not an inheritance; or
- it holds music (`group_chords_in_measure` is non-empty) — whatever clef was in
  effect there is the clef the exported pitches were resolved under.

Both conditions are load-bearing. Without the first, the rule would overrule a
genuine clef printed at a system head. Without the second it could claim an
opening clef under which notes already written out were not resolved — the
measures it skips emit a whole-measure rest either way, so skipping them cannot
move a pitch. It returns 0 — today's behaviour exactly — when nothing qualifies,
and the whole leading RUN is overridden rather than just measure 0, because
leaving a second furniture cell on the default would emit a clef change back to
it and another one away again.

Applied only where the staff BEGINS a part (`not state`), so a later system's
staff continuing a stitched part is untouched.

### Measured

Export-only, so every row was re-exported from its existing `omr.json` — no
transcription, no CPU window needed.

| row | clefs changed | export |
|---|---|---|
| Dvořák 9 | 7 parts: `m1:G2,m2:F4` → `m1:F4` (×5), `m1:G2,m2:C3` → `m1:C3` (×2) | changed |
| Brahms 1, Beethoven ×2, Mahler 5 | none | **byte-identical** |

Brahms is the control RESULTS.md named — its furniture cell is at the END of the
system, so its measure 0 is genuine and its fourteen clefs including an alto and
a tenor were already right. It stays byte-identical, which is what the rule
firing only on a leading furniture cell should look like.

**Canonical: provably unchanged.** All three engraved works re-export
byte-identically in MusicXML, and `_first_clef_bearing_measure` returns 0 for
every staff of all three — the rule is inert there, not merely neutral. The
LilyPond output is identical with the rule forced off, which is the same thing
said the other way. No canonical run was needed to establish this and none was
spent.

### ⚠️ It costs 0.0032 on the row it fixes, and the reason is item 1

| Dvořák arm | OMR-NED | edits | pred syms | `wrong clef` |
|---|--:|--:|--:|--:|
| A baseline | 0.5873 | 955 | 834 | 8 |

Arms C and D were previewed by deleting measure 0 from the JSON before export
(`scratchpad`, not committed) — the real fix 4 is measured below.

Two things to read off it. **`wrong clef` gets worse while the clefs get
right**: the spurious measure is still there, so musicdiff aligns our measure 2
against truth's measure 1, and moving the clef declaration back into measure 1
moves it into the bar that alignment discards. The clef is now correct in a bar
the metric does not look at. **And D equals C exactly** — with the furniture cell
gone, `_first_clef_bearing_measure` returns 0 on every Dvořák staff and fix 1 is
a no-op on this corpus.

So fix 1 is **dominated by fix 4 on the only row that can test it**, and this is
recorded rather than hidden. It is kept for three reasons that the pooled figure
cannot express:

1. the exported file is notationally correct — seven parts stop claiming a
   treble clef the page does not print, which is what a human opening the
   MusicXML sees, and the same trade CLAUDE.md records for chord order
   (`+2 edits, 46 notes out of the wrong class`);
2. **LilyPond is not covered by fix 4's benefit at all in the general case** and
   has no clef-change to recover with — there, a leading furniture cell is the
   difference between `\clef bass` and `\clef treble` for the whole staff;
3. it is the standing answer for any leading-furniture cell that fix 4's

The 7 fewer predicted symbols with 1 more edit is also, for the record, the
symmetry trap RESULTS.md documents in the resolution arm — the denominator moved
further than the numerator.

## Fix 2 — the margin crop still clips, on four publishers out of five

Ranked item 5. `tools/omr/staff_labels_vision.py`.

### First, a correction to the work order

RESULTS.md attributes `ken in C u. G`, `larinetten in B` and `competen in C` to
the Dvořák Simrock row. They are **Brahms**, Breitkopf *Sämtliche Werke*.
Dvořák's row had **zero** unresolved labels. The three rows that carried
rejected labels were Brahms (6), Beethoven 984073 (2) and Mahler (3).

### Why the 2026-08-31 fix did not travel

It was measured on **one publisher**. `crops-w14/20/26` are twelve systems of
Beethoven 5 and Beethoven 6, and the conclusion "20 is the smaller change that
gets the whole benefit" is true of that corpus and of nothing else.

`probe_margin_reach.py` (new, in this directory) measures the *printing* rather
than the reader: for each staff it walks left from the crop's own `x_ref` and
reports the margin ink runs in staff spacings — the unit `MARGIN_SPACINGS` is
written in, and the only one that transfers between a 2897-px scan and a
5409-px one. Over the five scan pages, 74 staves:

| edition | furthest label | staves the 20-spacing crop cuts |
|---|--:|--:|
| Dvořák, Simrock 1894 | 20.3 | 3 of 15 |
| Beethoven 5, IMSLP 575951 | 22.5 | 2 of 12 |
| Beethoven 5, IMSLP 984073 | 22.9 | 2 of 12 |
| Brahms 1, Breitkopf | 24.9 | 6 of 14 |
| Mahler 5, Peters | 26.4 | 11 of 19 |

**Twenty cuts a label on all five, including the edition the fix was made on.**
The 14 → 20 move fixed the failures its corpus *reported* without checking
whether ink still crossed the boundary — and on Beethoven 984073 it still did,
on exactly the two staves whose labels this benchmark then found rejected.

The correspondence is one-to-one, which is what makes this a diagnosis rather
than a plausible story:

`Carinetti` looked like an internal OCR slip and is not one — staff 2 is cut at
20 and the `Cl` ligature is what the crop lands on.

### The rule: 20 → 30, placed in a measured empty band

The probe searches **45** spacings out and finds nothing at all beyond 26.4 on
any of the 74 staves. So there is an 18-spacing gap with the entire corpus on
one side, and 30 sits in it — the same shape of decision as
`STEM_MAX_HEIGHT_LINES`, not a bump to make one case pass.

Widening costs no resolution: `build_margin_crop` downscales on
`max(width, height)` and a system's crop is far taller than wide, so the scale
factor does not move.

## Fix 3 — `Basso` never resolved because it was fed to its own judge

Ranked item 6. `tools/omr/contextual.py`, `tools/omr/score_layouts.py`.

### The mechanism, in two gates

`instruments.AMBIGUOUS_ALIASES` lists `basso: ("Bass voice", "Contrabass")`
with a comment saying position settles it, and
`contextual._resolve_ambiguous_labels` exists to let position do exactly that —
yet Beethoven 5 p.1 reported `ambiguous_labels_resolved: 0` and exported its
bottom staff as **Bass voice**, a singer. Two gates stood in the way and
**neither one alone accounts for it**, which is why it had stayed dormant.

**Gate 1 — the ambiguous reading is an input to the prior meant to overturn
it.** `fit_layouts` is handed `{slot: instrument}` for every slot a label named,
and slot 11's label had already resolved to `Bass voice`. No orchestral layout
has a voice anywhere, so the aligner can place that staff in **none** of them
and every voter abstains. Measured at slot 11 of that page:

| labels handed to `fit_layouts` | winning layout | ballot at slot 11 |
|---|---|---|
| …with `11: "Bass voice"` | `classical-shared-bass` | **`{}`** — empty |
| …withheld | `classical-condensed` | `{Contrabass: 0.643, Cello: 0.357}` |

The prior was not biased, it was **silenced** — and `classical-shared-bass`, the
one layout with no eleventh part at all, won precisely because it was the only
one not penalised for a staff it never has to explain.

`score_layouts` already documents this rule for PINS — *"an ambiguous alias …
POSITION settles those, and a pin is the one move that takes position off the
table"* — and the fit was doing the same thing more quietly. So
`_ambiguous_label_slots` withholds them.

**Gate 2 — the resolver asked a wider question than it needed answered.** Even
withheld, the ballot is 0.643 Contrabass / 0.357 Cello, below `MIN_AGREEMENT`
(0.75), so `assignment[11]` is None and `resolve_ambiguous_label` gave up. But
the twelve-way question "which instrument is this staff" being unsettled does
not unsettle the two-way question actually being asked: **not one voter put a
voice there.** `LayoutFit` now carries the whole ballot (`support`), and where
there is no agreed reading the resolver consults it and chooses a candidate only
when it is the only one of them with any support at all.

Unanimity among the candidates rather than a share threshold, because the
question is two-way; `MIN_AGREEMENT` is calibrated for "which of a dozen", and
reusing it here asks a two-way choice to clear a twelve-way bar. A ballot
backing **both** candidates is a genuine disagreement about this very question
and still abstains — as does a page whose layouts agree on something the alias
cannot mean.

### Measured

|---|--:|---|---|
| Beethoven 5, 984073 | 0 → **1** | Bass voice → **Contrabass** | 0.7119 → 0.7119 (1305 → 1305) |
| Beethoven 5, 575951 | 0 → **1** | Bass voice → **Contrabass** | 0.7479 → 0.7479 (1454 → 1454) |
| Mahler 5 | 0 → **1** | — | 0.8412 → **0.8408** (1684 → 1680) |
| Dvořák 9 | 0 → 0 | — | 0.5907 → **0.5905** (957 → 956) |
| Brahms 1 | 0 → 0 | — | 0.9352 → **0.9351** (3692 → 3689) |

Same tree, fix 3 the only change between the arms. Both Beethoven rows are
identical to the edit while the singer disappears from the foot of the score —
part naming does not reach OMR-NED, which is the documented behaviour and the
reason this item needed a correctness argument rather than a metric one.

The three rows that report `0` still moved by a few edits, and that is fix 3
too: `Bassi` and `Tp.` are ambiguous aliases as well, so those slots are now
**withheld from the fit** even where the resolver then abstains. Every such
movement is a small improvement (−1, −3, −4 edits) and none is large enough to
argue from.

**Canonical: inert by construction and checked.** `_ambiguous_label_slots` and
`_resolve_ambiguous_labels` both iterate the labels a READER returned, and the
engraved fixtures have `label_tiers` all zero — there is no ambiguous alias to

## Fix 4 — system furniture read as a measure

Ranked item 1. `tools/omr/transcribe.py`.

Content is what separates furniture from a measure, and content only exists
after detection — so the pass lives in `transcribe`, not `measure_extractor`,
which slices cells out of the page image before the detector has run. It sits
after the two dedupers, so the test sees the detections everything downstream
will see, and before the meter passes, so a courtesy meter caught as a bar
cannot vote on the page's time signature.

### Width was already refused; content is asked at the SYSTEM level

RESULTS.md priced width and rejected it — genuine measures 4.2 to 28.7 staff
spaces against 2.2 and 3.5 for the two spurious ones, a 0.7-space gap. It would
also have missed the second case found here, which is 12.5 spaces wide.

The level matters as much as the signal. **A barline spans the system**, so a
measure column is furniture for every staff of a system or for none of them.
Per-staff emptiness says nothing — any staff may be tacet — while a column
where not one staff of fifteen carries a notehead or a rest is a different
object, because a genuine measure on even a fully tacet staff contains its
whole-bar rest. "Has music" is `voicing.group_chords_in_measure`, the
**exporter's own** test for whether a measure needs a whole-bar rest, so the
rule and the thing it protects cannot drift apart.

### The measurement (`probe_furniture_columns.py`)

**243 measure columns, 27 systems, 20 committed transcriptions** across the
corpus-widening set, the engraved orchestral benchmark, the scan rows and the
key-signature artifacts. Exactly **two** columns carry no notehead and no rest
on any staff — **0.82%** — and both are furniture:

| file | sys | col | staves | px | spaces | content |
|---|--:|---|--:|--:|--:|---|
| dvorak-sym9-mvt1-405834-p5 | 0 | 0 of 9 | 15 | 56 | 2.20 | `structural ×17` |
| wtc-p17 | 1 | 0 of 4 | 2 | 463 | 12.51 | `clef ×2, accidental ×8, structural ×5` |

The WTC case was **not** one of the two RESULTS.md found, and it is the one that
proves content over width: 12.5 spaces is squarely inside the genuine range.
Every other system on that page — 0, 2, 3, 4, 5 — carries its clef and key
signature inside a first measure that also plays (1441, 1426, 1525, 1406 px,
19–22 noteheads each). Only system 1 has the header split off as its own cell.

### ⚠️ Leading and trailing columns only

A spurious barline in the MIDDLE of a system splits one bar into two halves that
**both still hold notes**, so a music-free middle column is far more likely a bar
the detector failed on — and dropping it would splice its neighbours together
and shift every measure number after it. Furniture is what sits *outside* the
music, at the ends a system's rules bound. A system with no music on any staff
is also left alone: that is a recognition failure, and deleting its measures
would turn a bad reading into no reading.

### Measured

| row | measures | OMR-NED | edits |
|---|---|--:|--:|
| **Dvořák 9** | **9/8 → 8/8** | **0.5905 → 0.5667** | **956 → 896** |
| Beethoven 984073 | 16/16 | 0.7119 → 0.7119 | 1305 → 1305 |
| Brahms 1 | 8/7 (unchanged) | 0.9351 → 0.9352 | 3689 → 3692 |
| Mahler 5 | 9/9 | 0.8408 → 0.8412 | 1680 → 1684 |
| Beethoven 575951 | 16/16 | 0.7479 → 0.7481 | 1454 → 1455 |

**Dvořák's number was PREDICTED before the run.** Deleting measure 0 from the
committed JSON and re-exporting gave 0.5665 / 895 edits; the pipeline change
measured 0.5667 / 896. A prediction confirmed to one edit is what makes this
attributable in a tree several workstreams are moving — see the caveat below,
which is why the ±1–4 edit movements on the other four rows are **not** claimed
here.

Nine of Dvořák's key signatures also move out of a spurious change at measure 2
into the opening bar — the same repair fix 1 made for clefs, obtained free.

### ⚠️ Two things this uncovered

**The staff-level summary goes stale, and that is not cosmetic.**
`staff["clef"]` is "what was in effect during the staff's FIRST measure", and
dropping a leading column moves which measure that is. `_lily_staff_block`
emits one `\clef` per staff from that field, so without a refresh this pass
would print treble for Dvořák's bassoon and both trombones — **and would do so
by disarming fix 1**, which had been recovering exactly those clefs from the
furniture cell that this pass now removes. A fix must not silently switch off
the fix that was covering the same case. `clef`, `key_signature` and
`time_signature` are refreshed from the new first measure; the exported
MusicXML is byte-identical either way (measures carry their own), so this is
LilyPond and JSON correctness, not a metric effect.

**Brahms is refused, with numbers.** Its trailing 113-px courtesy-meter cell
holds nine `noteheadWhole*` detections at confidence 0.28–0.74 sitting exactly
on the printed `9`s and `8`s — the bowls of the digits, the family CLAUDE.md
documents under *"the cell's own edge is not a notehead"*. So the column is
**not** music-free by the exporter's own test, and the rule correctly declines
it. Catching it needs one of two things already priced and refused:

- the width threshold, in a 0.7-space gap on five pages; or
- a fraction-of-staves-playing bar. Brahms's column has 3 of 14 "playing"
  against 13/14 and 14/14 for its genuine ones, which looks separable — and is
  not. A bar where 12 of 14 orchestral staves are tacet is ordinary music, and
  the 27 systems measured here contain no solo bar to prove otherwise. That is
  the "does this harness contain a case where what I changed would matter"
  question, and the answer is no.

The real lever is the notehead false positive, which is detector work, not
measure work. **Brahms stays 8/7.**

Tests: `test_measure_extractor.py::TestFurnitureMeasuresAreDropped` (7),
including the three the rule must NOT fire on — a column one staff plays, a
silent column in the middle, and a system with no music anywhere.

## ⚠️ Method note: the tree moved twice under this round, and once mid-run

Two of the four fixes were measured against arms run minutes apart, and that
was not always enough. Between the fix-3 scan run and the fix-4 one **no commit
landed**, yet Brahms moved 3689 → 3692, Mahler 1680 → 1684 and Beethoven 575951
1454 → 1455 — on a fix that provably drops zero cells from any of them. The
cause was an **uncommitted** 52-line edit to `tools/omr/rhythm.py` from another
workstream, which arrived in the working tree between the two runs.

So the honest reading of this round's per-row table is:

- **Dvořák's −60 edits is real**, because it was predicted from the JSON to
  within one edit before the pipeline change was run at all;
- **the ±1–4 edit movements elsewhere are noise from a shared working tree**,
  and are reported rather than attributed;
- `git log` is not sufficient to establish a stable base in a session like
  this. `git status` is — an uncommitted edit to a pipeline file moves numbers
  exactly as a commit does, and leaves no trace in the history to find it by.

The fix-2 A/B is the one arm of this round that is clean: both its arms ran
back to back with nothing else changing, and both gave identical figures on all
four rows.
