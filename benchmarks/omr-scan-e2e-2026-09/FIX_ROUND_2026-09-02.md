## Fix 1 — a part's opening clef is not always measure 0's

Ranked item 2. `tools/omr/export.py`.

### The mechanism, which is one step narrower than RESULTS.md states it

RESULTS.md says the export takes each part's clef from measure 0 and therefore
"all fifteen parts export as G2". Read against the file, the MusicXML is
slightly better behaved than that and it does not change the diagnosis: seven
parts open G2 **and then emit a clef change at measure 2** to the clef they
should have opened in (`m1:G2,m2:F4`). The other eight are treble throughout and
correct. LilyPond has no such recovery — `_lily_staff_block` emits one `\clef`
for the whole staff from `staff["clef"]` — so on that exporter all fifteen
Dvořák staves really are treble.

Underneath, `staff["clef"]` is `'treble'` on all fifteen staves, and so is
`measures[0]["clef"]`, while `measures[1..8]["clef"]` carries the right answer
on seven of them. The reason is visible in the detections:

| | measure 0 | measure 1 |
|---|---|---|
| Dvořák staff 3 (Fagotti) | `['structural']` — a brace at conf 0.33 | `['accidental','clef','notehead','rest','structural']` |
| Dvořák staff 1 (Flauto II) | `[]` — nothing at all | `['accidental','clef','rest','structural','time_sig_digit']` |

Every one of the fifteen leading cells holds **no clef detection**: eleven hold
only `structural`, four hold nothing. `transcribe` reads a clef where one is
printed, and system furniture prints none — so measure 0's clef field is the
positional default, and measure 1's is a reading.

### The rule

`export._first_clef_bearing_measure(measures)` returns the index of the first
measure that could have READ a clef or could have USED one:

- it holds a `clef` detection — its clef is a reading, not an inheritance; or
- it holds music (`group_chords_in_measure` is non-empty) — whatever clef was in
  effect there is the clef the exported pitches were resolved under.

Both conditions are load-bearing. Without the first, the rule would overrule a
genuine clef printed at a system head. Without the second it could claim an
opening clef under which notes already written out were not resolved — the
measures it skips emit a whole-measure rest either way, so skipping them cannot
move a pitch. It returns 0 — today's behaviour exactly — when nothing qualifies,
and the whole leading RUN is overridden rather than just measure 0, because
leaving a second furniture cell on the default would emit a clef change back to
it and another one away again.

Applied only where the staff BEGINS a part (`not state`), so a later system's
staff continuing a stitched part is untouched.

### Measured

Export-only, so every row was re-exported from its existing `omr.json` — no
transcription, no CPU window needed.

| row | clefs changed | export |
|---|---|---|
| Dvořák 9 | 7 parts: `m1:G2,m2:F4` → `m1:F4` (×5), `m1:G2,m2:C3` → `m1:C3` (×2) | changed |
| Brahms 1, Beethoven ×2, Mahler 5 | none | **byte-identical** |

Brahms is the control RESULTS.md named — its furniture cell is at the END of the
system, so its measure 0 is genuine and its fourteen clefs including an alto and
a tenor were already right. It stays byte-identical, which is what the rule
firing only on a leading furniture cell should look like.

**Canonical: provably unchanged.** All three engraved works re-export
byte-identically in MusicXML, and `_first_clef_bearing_measure` returns 0 for
every staff of all three — the rule is inert there, not merely neutral. The
LilyPond output is identical with the rule forced off, which is the same thing
said the other way. No canonical run was needed to establish this and none was
spent.

### ⚠️ It costs 0.0032 on the row it fixes, and the reason is item 1

| Dvořák arm | OMR-NED | edits | pred syms | `wrong clef` |
|---|--:|--:|--:|--:|
| A baseline | 0.5873 | 955 | 834 | 8 |
| B **fix 1 only** | **0.5905** | 956 | 827 | 12 |
| C fix 4 only (measure 0 dropped) | 0.5665 | 895 | 788 | 4 |
| D fix 1 + fix 4 | 0.5665 | 895 | 788 | 4 |

Arms C and D were previewed by deleting measure 0 from the JSON before export
(`scratchpad`, not committed) — the real fix 4 is measured below.

Two things to read off it. **`wrong clef` gets worse while the clefs get
right**: the spurious measure is still there, so musicdiff aligns our measure 2
against truth's measure 1, and moving the clef declaration back into measure 1
moves it into the bar that alignment discards. The clef is now correct in a bar
the metric does not look at. **And D equals C exactly** — with the furniture cell
gone, `_first_clef_bearing_measure` returns 0 on every Dvořák staff and fix 1 is
a no-op on this corpus.

So fix 1 is **dominated by fix 4 on the only row that can test it**, and this is
recorded rather than hidden. It is kept for three reasons that the pooled figure
cannot express:

1. the exported file is notationally correct — seven parts stop claiming a
   treble clef the page does not print, which is what a human opening the
   MusicXML sees, and the same trade CLAUDE.md records for chord order
   (`+2 edits, 46 notes out of the wrong class`);
2. **LilyPond is not covered by fix 4's benefit at all in the general case** and
   has no clef-change to recover with — there, a leading furniture cell is the
   difference between `\clef bass` and `\clef treble` for the whole staff;
3. it is the standing answer for any leading-furniture cell that fix 4's
   deliberately conservative content test declines to remove.

The 7 fewer predicted symbols with 1 more edit is also, for the record, the
symmetry trap RESULTS.md documents in the resolution arm — the denominator moved
further than the numerator.
