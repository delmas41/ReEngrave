# Slurs — the sixth detected-and-never-exported gap, and the one that needed a
# change to the event model

**2026-09-01.** `export.annotate_slurs` had been written, tested and
deliberately **not wired in** since `89277a2`, with its reason measured rather
than suspected and recorded in its own docstring:

    dynamics only        pooled 0.2595   1811 edits
    dynamics + slurs     pooled 0.2598   1835 edits   `wrong slur` 76 -> 97

(Those two rows, and every "pre-ledger" table below, predate `81446a0`.)

Cells are cut per MEASURE, so a slur crossing a barline is detected as **two
arcs**, and emitting them per measure writes two slurs where the music has one.

This is the fix. **Pooled 0.2263 → 0.2209**, Brahms **0.3302 → 0.3185**,
`wrong slur` **81 → 61**, edits **1584 → 1563**.

⚠️ **Measured on top of the cross-staff ledger fix (`81446a0`), not before it.**
An earlier pass of this same work read 0.2449 → 0.2394 on the pre-ledger base;
that base is gone and those numbers are superseded. The step sizes barely moved
(−0.0055 then, −0.0054 now), which is some evidence the two fixes are
independent. Every intermediate row below that is labelled *pre-ledger* was
taken on the old base and is kept because it is what the reasoning turned on.

---

## The thing that had to change was smaller than it looked

The handoff called for "a slur that can outlive a measure in the event model".
It turned out the event model needed nothing at all.

**A MusicXML slur is already free to open in one measure and close in another**,
and LilyPond's `(` `)` have never cared about barlines. All either format needs
is a number that means the same thing at both ends. What was per-measure was not
the *model* but the *pairing*: `annotate_slurs(events, detections)` ran once per
cell and could not see the other half of its own arc.

So the pairing moved to the **staff**, in **page pixels** — the only frame
shared across cells. That is the same move `transcribe._pair_ties_in_staff`
already makes for exactly the same reason, and its docstring says so: ties
spanning a barline are most ties in real music.

The arc-to-note mapping, the part that was always right, is unchanged.

## Two constants, both read off a gap

Nothing here is a tuned threshold. Each was measured on the Brahms fixture
first and the constant placed in the empty space the measurement found.

**Where a split arc ends.** An arc clipped by a cell boundary ends EXACTLY on
it. Facing edges of a consecutive-measure pair, in staff spaces:

| | value |
|---|---|
| the 16 pairs that are one slur | **0.00 – 0.05** |
| the nearest pair that is not | **1.75** |

Anything in that gap gives the same 16 merges; `_SLUR_BOUNDARY_SPACES = 0.5`.

**How far apart the two halves may sit vertically.** A slur crosses the barline
at the height it left:

| | value |
|---|---|
| genuine continuations | **0.00 – 0.53** |
| next-nearest candidate | **8.05** |

The 8.05 group is an arc ABOVE the staff paired against one BELOW it — two
different slurs that merely share a barline. `_SLUR_CONTINUATION_DY_SPACES = 2.0`.

## The half that made it real: the arc is narrower than the run it binds

Merging alone moved the pooled score 0.2449 → 0.2436 *(pre-ledger)* and **that
number was an artifact**. Read the whole row:

*(pre-ledger base)*

| | pooled | edits | pred syms | `wrong slur` |
|---|--:|--:|--:|--:|
| baseline (no slurs) | 0.2449 | 1715 | 3308 | 77 |
| merge only | 0.2436 | **1724** | 3382 | **86** |

Edits went UP and the slur category got WORSE. The score fell only because
OMR-NED's denominator sums BOTH sides, so 74 new predicted symbols diluted a
9-edit loss. This is the symmetry caveat in `FINDINGS.md` doing real damage to a
real conclusion — **always read the edit count beside the ratio.**

The cause was visible the moment the slurs were compared to the truth note by
note rather than counted. On the Contrabass, where the truth slurs `n0 → n5` in
all seven bars:

```
TRUTH                    PREDICTION (merge only)
m1 n0 -> n5              m1 n1 -> n4
m2 n0 -> n5              m2 n0 -> n5   ✓
...                      m6 n1 -> n4
m7 n0 -> n5              m7 n1 -> n4
```

**A slur is drawn between its noteheads**, from just above the first to just
above the last, so the ink stops a hair inside both outer centres and an
unpadded x-test drops the outer note at each end. Of the 75 notehead centres
lying just outside an arc, **54 sit within 0.19 notehead widths of its edge and
the next is at 0.32** — the same two-cluster shape as the other two constants.

So the arc box is padded, which is precisely the correction
`rhythm._beamed_groups` already makes to a beam box, for a related reason (a
beam starts at the first *stem*, a notehead's width from the centre).

The pad is a plateau, not a peak — 0.25 and 0.5 give identical scores:

*(pre-ledger base)*

| pad (notehead widths) | pooled | edits | `wrong slur` |
|---|--:|--:|--:|
| 0.0 | 0.2436 | 1724 | 86 |
| **0.25** | **0.2397** | **1698** | **60** |
| 0.5 | 0.2397 | 1698 | 60 |
| 1.0 | 0.2399 | 1699 | 61 |

With the pad the Contrabass is **7/7 exact**.

## Both ends must land in the same voice

MusicXML pairs `<slur>` **within a `<voice>` stream**. 3 of 75 slurs opened in
voice 1 and closed in voice 2, leaving three unpaired starts and three orphan
stops — a file that is malformed rather than merely wrong. Trimming each slur to
the longest run its arc covers inside ONE voice fixed all six and took
`wrong slur` 60 → 57.

A validity sweep over the emitted file now reports no unpaired slur in any part
or voice.

## What this is worth, and what is left

Scoring the SAME prediction against a truth with every `<slur>` stripped out
prices the whole opportunity:

| | pooled | edits |
|---|--:|--:|
| baseline vs normal truth | 0.2263 | 1584 |
| baseline vs slur-stripped truth | **0.2171** | 1502 |

All 82 of Brahms's slurs cost exactly 82 edits, so a *perfect* slur reader would
land near **0.2121** (82 edits removed and 82 predicted symbols added). This
change takes **0.2263 → 0.2209**, about **38%** of that.

**The rest is not slur work.** The Cello shows what the residue is:

```
TRUTH                          PREDICTION
m1 n0 C4  -> m2 n4 F4          m1 n0 C4  -> m2 n4 F4    ✓ crosses a barline
m3 n0 G4  -> m4 n3 A-4         (missing)
m5 n0 A-4 -> m5 n5 F4          m5 n0 A-4 -> m5 n5 F4    ✓
m6 n0 F4  -> m6 n5 D4          m6 n0 F4  -> m6 n5 A-4   indices right, pitch wrong
m7 n0 D4  -> m7 n9 B-3         m7 n0 A-4 -> m7 n9 F4    indices right, pitch wrong
```

Two of the four have the right note INDICES and the wrong pitches. That is note
recognition, on a page whose note recall is 0.824 — a slur cannot land on a note
stream that is wrong, and chasing it from the slur side will not help.

## Containment

- **Beethoven and Mahler export BYTE-IDENTICALLY.** Neither page carries a slur
  the detector reads, so neither moves by an edit.
- Brahms differs in **no line that is not a `<slur>` or its `<notations>`
  wrapper** — 396 changed lines, 0 of them anything else.
- The authored fixtures are unchanged: the pass writes only `slur_states` and
  touches no pitch, duration or segmentation.
- LilyPond output compiles to PDF with no new diagnostics.

## Reproducing

```bash
python3 -m tools.omr.training.orchestral_eval --omr-ned
```

The per-step numbers above came from exporting a CACHED transcription rather
than re-running detection each time — `to_musicxml` is a pure function of the
JSON, so the export loop costs seconds instead of the minutes a full eval takes.
The cached baseline reproduced the committed 0.2449 exactly, which is what
licenses reading the intermediate rows.
