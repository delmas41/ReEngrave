# Three margin labels the lexicon dropped — three different faults

**2026-09-03.** Running `benchmarks/omr-scan-e2e-2026-09/scan_eval.py` over the
five verified scan rows produced three margin strings `instruments.lookup`
could not match. A dropped label is not a small loss: the staff then behaves as
UNLABELLED, and a label is what anchors `dossier.join_parts_to_slots`, so the
part↔staff join loses a pin.

They turned out to be three different KINDS of fault, which is most of the
value in this file — only one of them is a lexicon bug at all.

| reported string | edition | what it is | where it is fixed |
|---|---|---|---|
| `Contrafagott` | Mahler 5 / local scan p2 | a lexicon gap, and one hole in a family of ~25 — eight of which resolved to the **wrong instrument** rather than abstaining | `instruments.py` |
| `Yiolino II.` | Dvořák 9 / Simrock p5 | an OCR V→Y | already fixed, unmerged, on `claude/zen-panini-fdc5ae` |
| `in C \frac{1}{2}` | Brahms 1 / Breitkopf p.1 | Surya's LaTeX for a **stacked part number** — plus a label that genuinely names no instrument | `staff_labels_surya.py` |

---

## 1. `Contrafagott` — the hand-list had six of twenty-five

**A contrabassoon is printed as a BASSOON name with a contra- qualifier**, and
the two halves vary independently: four languages of noun (`fagotto` /
`fagott` / `basson` / `bassoon`, each with plural and abbreviation) against four
of qualifier plus the abbreviations a crowded margin actually uses (`C. Fag.`,
`Cfg.`, `Cont. Fag.`). The spellings are a CROSS PRODUCT. The hand-list held
six of them.

⚠️ **The missing spellings did not ABSTAIN.** The bassoon noun inside them
matches on its own and the qualifier is ignored, so the failure is a wrong
instrument, not a missing one:

| printed | before | after |
|---|---|---|
| `Contra-Fagott` | **Bassoon** (medium) | Contrabassoon |
| `Kontra-Fagott` | **Bassoon** (medium) | Contrabassoon |
| `Contra Fagotto` | **Bassoon** (medium) | Contrabassoon |
| `C. Fagotto` | **Bassoon** (**high**) | Contrabassoon |
| `Contra Bassoon` | **Bassoon** (medium) | Contrabassoon |
| `Contre-basson` | **Bassoon** (medium) | Contrabassoon |
| `Cont. Fag.` | **Bassoon** (medium) | Contrabassoon |
| `Contra Fg.` | **Bassoon** (medium) | Contrabassoon |
| `Contrafagott` `Contrafagotti` `Kontrafagotte` `Kontrafagotti` `Contrafag.` `Kontrafag.` `Contrabasson` `Cfg.` `Kfg.` | — | Contrabassoon |

`C. Fagotto` → Bassoon at **high** confidence is the one that matters most: a
high-confidence unambiguous read is exactly what pins a staff to a part. This
is the same failure the `C. Fag.` comment in `instruments.py` already recorded
— fixed once, for one spelling, in 2026-08.

**So the set is DERIVED, not hand-listed** — the move `VOICE_QUALIFIERS` made
for the same reason, and for the reason the `Tr. Alt.` findings give: *a
hand-list of a cross product is a bug with a slow fuse*. `_CONTRA_ALIASES` is
`{contra, kontra, contre, cont, kont, double, c, k}` × the bassoon's own ten
aliases × `{closed, spaced}`, 160 strings, and every one of the six previously
hand-listed aliases is regenerated by it (pinned by a test in both directions).
`contraf` — Mahler's "Contraf." — is kept beside it because it is a
TRUNCATION rather than qualifier-plus-noun, so no cross product makes it.

⚠️ **This does not loosen matching.** Every generated string still has to
appear in the label, word-bounded, exactly; the gate is untouched and the
vocabulary is completed. `Ctrfg.` is plausible and unevidenced, so it is left
out rather than guessed at.

The plain bassoon is unaffected because every generated alias is LONGER than
the bassoon alias inside it, and `_ALIAS_INDEX` is longest-first.

## 2. `Yiolino II.` — already answered, and the answer was measured

`claude/zen-panini-fdc5ae` (commit `6bfed41`, 2026-09-02) fixed exactly this
and has not been merged. Its assessment is
[`../omr-margin-labels-2026-08/OCR_CONFUSIONS_2026-09-02.md`](../omr-margin-labels-2026-08/OCR_CONFUSIONS_2026-09-02.md);
it is merged into this branch rather than rebuilt.

The deliberate decision the request asks for, as that branch made it:

- **The fold belongs in the lexicon** — `instruments._OCR_FOLD` has existed
  since 2026-08-28, already covers the i/l/1 stroke group and o/0, is applied
  to alias and candidate alike, runs only as a FALLBACK after exact matching
  fails, and marks anything it produces `ocr_folded` → `confidence == "low"`.
  `y → v` is one line in a mechanism already built for this.
- **The admission rule is RARITY, not plausibility.** `y` occurs in two
  aliases (`tympani`, `xylophone`) and both resolve on the exact pass before
  the fold is ever reached, so folding it collides with nothing: 0 collisions
  over all 260 aliases, 0 net-new cross-instrument collisions, 0 corpus
  changes.
- **Common-letter confusions are refused by name** — `a/u`, `b/h`, `c/e`,
  `n/m` — and the refusal is priced rather than asserted: the corpora's own
  unread `Fug.`→`Fag.` and `Oh.`→`Ob.` need exactly those pairs and stay
  unread. A gated single-substitution matcher was prototyped, measured
  collision-free, and **not adopted**, because its only gain was that one read.
- **`rn/m` is out**: a two-character confusion no 1:1 fold can express, with no
  corpus evidence, and it would ride on the rejected matcher.

That is the answer to "lexicon or reader": **the lexicon, for a fold; the
reader, for markup** — which is what §3 is.

## 3. `in C \frac{1}{2}` — markup, and a label that names nothing

Two separable things, and only one is fixable.

**The markup is Surya's.** Surya 2 returns each block as HTML
(`_surya_worker._text_of` already unwraps that), and it writes a STACKED pair
of numerals as a LaTeX fraction — because a stack is what the page prints.
Breitkopf's Brahms 1 puts the horn part numbers `1.` over `2.` beside `in C`,
so the reader returns `in C \frac{1}{2}`; the Es horns come back as
`in Es \frac{3｜4}`, one brace pair and a fullwidth bar where the rule is.

The digits are PART NUMBERS, which `instruments.normalize_label` already
exists to drop. The CONTROL WORD is not a number, and survives into the matched
string:

| string | resolves to | coverage | confidence |
|---|---|--:|---|
| `Clar. 1.2.` | Clarinet | 1.00 | **high** |
| `Clar. \frac{1}{2}` | Clarinet | 0.50 | **medium** |

⚠️ **Read that at its real size.** `confidence` is not a hard gate — pinning in
`dossier.join_parts_to_slots` turns on whether an alias is AMBIGUOUS, not on
confidence — so this demotion is diagnostic noise (`low_confidence_labels`)
rather than a lost pin. It is worth fixing because it is free and because the
raw `StaffLabel.text` a human reads back should be the label, not the markup;
it is not worth claiming a recovered staff for.

**Folded at the reader, not in the lexicon.** LaTeX is Surya's output format,
not something a printed margin contains, and this is the same boundary where
the worker's HTML is already turned into plain text. Teaching the lexicon
markup would put one reader's quirk in the module every reader shares. The
braces and the bar are stripped ONLY from strings that carry the control word,
because `instruments._OCR_FOLD` reads a `|` as an `i` — a part number `II.`
comes back as `||.` often enough that deleting bars everywhere would cost more
than the markup does.

**The other half is not a lexicon problem and is not fixed.** `in Es 3 4`
names no instrument even after the markup is gone, and abstaining is the right
answer: Breitkopf prints the noun `Hörner` ONCE, braced across the pair of horn
staves, so the second staff's margin genuinely holds only a key and a number.
Recovering it needs a staff to inherit the noun from its brace-mate — a
contextual-layer rule about what a brace means, with its own multi-edition
measurement — not a wider lexicon.

## Validation — three corpora, per the standing rule

The rule from `LEXICON_TR_ALT_2026-08-31.md` is that a lexicon change passing on
one corpus means nothing. Same three measurements, none of them new.

### 0. Every part name the reference encodings hold — the widest net

`reference_part_names.py`: **1271 distinct** `<part-name>` / `<part-abbreviation>`
/ `<instrument-name>` strings from all 1745 MusicXML files in
`library/reference/`. Resolved with both lexicons:

```
1271 labels, 1 changed
   1x  'Contrafagott.'      —  ->  Contrabassoon      ['' -> 'contrafagott']
```

Nothing else moves. As that file says, this proves a change breaks nothing
across a very wide vocabulary and almost nothing about it working — engraving
software writes `Contrabassoon`, not the printed `K. Fag.`. (Different from the
5507 that doc quotes: that counted the Gradus tree plus raw PDF text spans.)

### 1. The reader benchmarks that already exist

`score_readers.py` over every committed results file, before and after:
`results.json` 25/25 agree 0 disagree, `results-surya.json` 24/24 0 disagree,
`results-surya-w14/20/26/30` and `results-vision-w14/20` all unchanged to the
count. **Byte-identical in both arms** — those crops carry no contrabassoon and
no markup, so this is a no-regression check and nothing more.

### 2. Every margin label thirteen editions actually produce — the one that counts

`read_margin_labels.py` runs the real readers over pages sampled through each
score and dumps the raw strings; `resolve_labels.py` replays the dump through
`origin/main`'s lexicon and the working tree's in one process.

⚠️ **This is a RE-SAMPLE, not the identical 1380.** That run's page list was
never committed, so `pages.json` here samples ten pages evenly through each
edition (plus the exact pages the scan benchmark scores). The ten editions are
the same ten, plus the three scan-benchmark editions that surfaced the faults.

⚠️ **BOTH readers run on every page here**, which is wider than production —
`contextual._labels_for_page` asks Surya only where the text layer came back
thin. Deliberate: a garbled OCR read is exactly the population a lexicon change
could misfire on. It is also the whole cost (~2.5 h, dominated by Surya on
dense margins); `--ladder` takes the production path instead.

**All twelve changes are the intended ones, and ten of them were not the bug
that was reported:**

```
   5x  'K-Fag.'        Bassoon  -> Contrabassoon    Brahms 1 / Breitkopf
   3x  'K.Fag.'        Bassoon  -> Contrabassoon    Brahms 1 / Breitkopf
   1x  'K-Fag'         Bassoon  -> Contrabassoon    Brahms 1 / Breitkopf
   1x  'K:Fag.'        Bassoon  -> Contrabassoon    Brahms 1 / Breitkopf
   1x  'Contrafagott'  —        -> Contrabassoon    Mahler 5   <- the report
   1x  'Yiolino II.'   —        -> Violin           Beethoven 5 / imslp-575951
```

⚠️ **The ten `K-Fag.` are the real find, and they were never an abstention.**
Breitkopf abbreviates Kontrafagott as `K. Fag.`, so on the SCAN BENCHMARK'S OWN
Brahms edition ten staves were reading as **Bassoon** — a confident wrong
instrument on a page that also prints two real bassoon staves. The reported
`Contrafagott` was the cousin that happened to abstain and therefore got
noticed. This is the case for deriving the set rather than adding the one string
that was reported.

⚠️ **`Yiolino II.` did not come back on Dvořák.** This run read that page
cleanly (15 labels, 0 unresolved) and the misread turned up on Beethoven 5
instead. Surya's nondeterminism on identical input is a recorded, unexplained
phenomenon — see the long comment in `contextual._labels_for_page`. The fold is
still worth having; a corpus that shows it once is not a corpus that will show
it in the same place twice.

### The markup fold changes zero resolutions, and that is the honest number

Scored both ways — lexicon alone, and lexicon plus
`staff_labels_surya._plain_text` on the head side (`--fold-reader-markup`) — the
tables are **identical**. The corpus holds exactly three LaTeX strings and not
one of them names an instrument either way:

```
  brahms1-breitkopf-scan p0 s5  'in C  \frac{1}{2}'   -> None  (plain: 'in C 1 2')
  brahms1-breitkopf-scan p0 s6  'in Es  \frac{3}{4}'  -> None  (plain: 'in Es 3 4')
  ravel-bolero-textlayer p40 s14
        'p^{\text{est}} = \frac{T_r}{R_e}'            -> None
```

So the demotion the fold prevents (high → medium, §3) is real in principle and
**unexercised by this corpus**: no label here carries markup AND a noun. It
ships because it is free, because the raw `StaffLabel.text` should be the label,
and because Surya emits markup on more than one edition — the Boléro string is a
whole equation hallucinated out of a margin, on a different publisher, in a
different language. It does not ship on a claim of recovered staves.

Note the Es horns came back `\frac{3}{4}` here where the report saw
`\frac{3｜4}`. Same nondeterminism; `_plain_text` handles both, and a test pins
the damaged form.

## `Hr.` / `Trpt.` — fixed the same day, once measured

The largest gap this sweep turned up was left open at first ("that is a third
lexicon change and it deserves the same multi-edition measurement rather than a
ride on this one"). Measured separately and shipped:

`hr` (German/English *Hörner*) and `trpt` — a distinct 4-letter shorthand from
the `tpt` already in the table, not a typo of it — were **0/409** collisions
against every existing alias, in both directions, and **0/1271** touches on the
reference part-name corpus. Against the same 1422-label margin dump: **24
labels, 13 distinct strings, 0 outside the Brahms 1 / Breitkopf horn and
trumpet staves** — more than the 18 first estimated, because that number was a
`.most_common(12)` truncation, not the real count:

```
   7x  'Trpt. (C)'        1x  'Trpt.'           2x  'Hr. (E)'
   4x  '(C) Hr.'          1x  'Hr. (Es)'        1x  '(E) Hr.'
   2x  'Hr. 1. (C) 2.'    1x  '(C) Hr'          1x  '(Es) Hr.'
   1x  'Hr. 1. (Es) 2.'   1x  '. (C) Hr.'       1x  '(F) Hr.'
   1x  'Hr.1. (Es)2.'
```

⚠️ **The transposition offset is exact only when the key TRAILS the alias.**
`Hr. (E)` parses to fifths_offset **-4** (E horn) correctly, because
`_parse_bare_key` reads the token after the matched alias. `(C) Hr.` — key
BEFORE the noun — falls back to Horn's positional default instead of reading
the parenthetical, and so does any trailing key with a stray part-number after
it (`Hr. 1. (C) 2.`, numeral eats the trailing-key regex's anchor). **This is
not new**: `A-Klar.` has resolved to Clarinet with its DEFAULT transposition,
not a parsed one, since 2026-08-31 — `_parse_bare_key` has only ever looked
after the alias, for every key-taking instrument in the table. Adding `hr` /
`trpt` inherits that limit rather than introducing it. The instrument NAME is
right in all 13 strings, which is what a dossier join pins on
(`unambiguous()`, not the offset); fixing the leading-key case is its own
change, with its own corpus, same as everything else in this file.

## Found here and NOT fixed — each is its own bug with its own corpus

**A whole margin can arrive as ONE label**, and it resolves to whichever
instrument the index reaches first: Beethoven 5's `'Fl. \n pic. \n ... Tr. \n
Bas.'` (the entire system's margin, 17 staves) resolves to **Piccolo**, and the
equivalent Mahler blob to **Trombone**. That is a reader/assignment fault, not a
lexicon one — one block was tied to one staff — and it is a confident wrong
answer, so it is worth its own look.

**`Veelle.` / `Voelle.`** — Mahler's `Vcelle.` with a c→e — stay unread, which
is the priced cost of refusing common-letter folds (§2). So does Mahler's
`Flüten` (Flöten with ü for ö).

**`Ctrfg.`** is a plausible contrabassoon abbreviation that no corpus here
prints, so it is deliberately not among the generated prefixes.

## Reproducing

```bash
# widest net, seconds
python3 benchmarks/omr-lexicon-2026-09/reference_part_names.py --out /tmp/part-names.json
python3 benchmarks/omr-lexicon-2026-09/resolve_labels.py /tmp/part-names.json --base origin/main

# the reader corpus: the dump is committed, so scoring is instant
python3 benchmarks/omr-lexicon-2026-09/resolve_labels.py \
    benchmarks/omr-lexicon-2026-09/labels.json --base origin/main --detail

# re-reading it is NOT instant — ~2.5 h, dominated by Surya on dense margins.
# `--ladder` takes the production path (Surya only where the text layer was
# thin) and is much cheaper.
python3 benchmarks/omr-lexicon-2026-09/read_margin_labels.py \
    --pages benchmarks/omr-lexicon-2026-09/pages.json --out labels.json

python3 -m pytest tools/omr/tests/test_instruments.py \
    tools/omr/tests/test_staff_labels_surya.py -q
```
